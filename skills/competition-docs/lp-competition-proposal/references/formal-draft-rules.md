# 正式版产出规范

正式版计划书与工作区草稿是两回事。草稿可以有状态、待确认、图片来源等管理内容；
正式版必须干净、正式、如实。本文件是正式版生成前的检查清单。

## 1. 去草稿味清单（正式版禁止出现）

- "待补充 / 待确认 / 待填写 / 待提供"等占位字样
- "图片来源（本块）"、"图片需求"、"状态：草稿"等管理性标题
- 赛事规则说明混入正文，如"团队规模符合赛事要求（不超过 15 人…）"
- 写给协作 AI 的话（"按赛事要求须上传…"、"本块内容归入…"等）
- 交叉引用工作区文件名（如"详见 10-草稿-xxx.md"），正式版引用用"见附录/见第 x 章"

处理方式：占位信息要么补真实内容，要么写成通顺的正式表述，不能留空壳注释。

## 2. 规划与事实分明（不吹牛）

| 项目状态 | 正确写法 | 错误写法 |
|---|---|---|
| 原型阶段 | "当前处于产品原型阶段，后续将推进标定与试点验证" | "已完成可落地产品" |
| 规划的应用场景 | "规划的目标应用场景为…" | "已在回收站部署…" |
| 落地计划 | "计划以辽宁作为首批落地地区，选择依据如下…" | "已在辽宁落地，建成…" |
| 预期价值 | "项目预期产生的社会价值体现在…" | "项目已实现社会价值…" |
| 预测数据 | "预期第一至三年收入约…" | 直接写确定数字不加"预期" |

原则：做过的事如实写（实验室实测、原型功能、专利受理），没做的事写"规划/计划/预期"。

## 3. 数据与来源

- 所有关键数据标注来源（来源名 + 年份），商业报告口径标注性质（如"商业报告"）
- 正文字数遵守模板限制（如"正文控制在 12000 字以内"）
- 论文、专利等支撑材料在附录列出，正文不展开堆砌

## 4. 结构、深度与衔接

- 章节结构严格按官方模板，不自创
- 重点章节（研究历程 / 产品 / 技术 / 市场 / 商业模式 / 财务）详细展开，
  用三级标题（如 1、1.1、1.1.1），主次分明
- 章节之间要有因果衔接，讲清"为什么这样做"，不跳逻辑
  （示例：研究历程验证可行性 → 切中行业需求（多点、组网、留痕）→ 因此设计检测端+中控端分离）
- 算法、架构等核心内容展开讲清楚（原理、模块、流程），不一句带过

## 5. 图片全量核对

- 对照 `image-map.md`，逐张核对用户提供的图片是否已插入正文
- 每张图要有图注 / 上下文说明，放在对应章节
- 未插入的图：要么补插到合适位置，要么向用户说明原因
- 图片引用统一 `![图注](images/xxx.png)`，路径正确
