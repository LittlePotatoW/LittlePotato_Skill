# LP_CompetitionProposal — 比赛项目计划书生成器

## 定位

把"代码 + 材料 + 调研"变成一份完整、可继续转 Word 的项目计划书 `.md`。
只做文档编排与调研补全，**不编造代码事实**。

## 开场必问（阶段 0）

开始前先按 `references/opening-questions.md` 一次性问齐，然后整理成材料清单让用户确认：

1. 代码文件夹在哪？
2. 计划书要求是什么？（评分标准/格式要求/章节要求，给文件或粘贴文字）
3. 能提供哪些材料？（已有草稿、比赛背景材料、图片、数据、访谈等）
4. 需要做到哪一步？
   - A：纯文字稿 + 图片需求清单
   - B：收集图片后生成正式版 .md
   - C：调研补全成最终 .md
   - D：最终 .md + 转 Word（衔接 lp-md2docx）
5. 比赛类型 / 目标评委？（决定章节侧重与调研深度）

用户确认材料清单后再进入阶段 1。

## 工作流程

### 阶段 1：出方案

- 依据计划书要求 + `references/proposal-structure.md` 定章节结构表
- 每章标注内容来源：代码分析 / 调研 / 用户材料 / 图片
- 列出图片需求清单（见 `references/image-checklist.md`）
- 把方案写进 `方案.md` 发给用户，**确认后才执行**

### 阶段 2：代码分析 → 纯文字稿

- 遍历代码文件夹：README、目录结构、技术栈、核心模块、关键实现
- 生成基于代码的章节纯文字稿：项目概述、技术方案、系统架构、功能实现、创新点、技术难点
- 同时输出"图片需求清单"：每章需要的图（架构图/流程图/界面截图/数据流图/部署图），标注 必需/建议
- 明确报告哪些必需图缺失、需要用户提供

### 阶段 3：图片收集 → 正式版 .md

- 用户提交图片，同时用口头 / 文字说明每张图的内容（只给文件名也行，AI 推断后请用户确认）
- AI 根据用户描述自动生成 / 更新 `images/image-map.md`：两列，图片相对路径 + 图片描述，
  给不能看图的 AI 提供图片内容信息（需要了解图片内容时读它，不猜图）
- 用 `scripts/check_images.py` 校验 md 图片引用与 `images/` 文件夹是否一致
- 缺失的必需图：询问"补图还是用文字替代"
- 图片统一整理进 `images/` 文件夹，按规范命名（见 image-checklist.md）
- 生成正式版 .md，图片引用全部指向 `images/`

### 阶段 4：调研补全

- 基于正式版 .md + 比赛背景材料，按 `references/research-dimensions.md` 调研
- 生成：项目背景、项目意义、竞品分析、市场与用户需求等章节
- 调研中新增的图片由用户说明后追加进 `image-map.md`
- 每处调研结论标注来源；不确定的标注"待确认"
- 材料不足时列出缺口清单询问用户，补充后再写，不擅自编造

### 阶段 5：最终交付

- 汇总成最终 .md 版计划书，图片统一放 `images/` 文件夹，`image-map.md` 随附交付
- 汇报：完成章节、未覆盖的要求、仍缺失的材料/图片
- 如需 Word：调用 lp-md2docx（`python ../lp-md2docx/scripts/convert.py 计划书.md`）

## 输出约定

- 最终产出：`计划书.md` + `images/` 文件夹 + `images/image-map.md`
- 中间产物：`方案.md`（阶段1）、`文字稿.md`（阶段2）、`图片清单.md`（阶段2）、
  `images/image-map.md`（阶段3 生成并持续维护）、`调研笔记.md`（阶段4）
- 不覆盖用户已有文件；新文件使用上述约定文件名，放在工作区

## 核心原则

1. 代码事实不编造：功能、技术栈以代码为准，不确定就标注并询问
2. 调研结论标来源，数据不确定标"待确认"
3. 每阶段结束先汇报再继续，不一次性闷头做完
4. 材料缺失时明确列出并询问，不擅自跳过必需内容
5. 图片命名规范、路径统一指向 `images/`
6. AI 看不了图片时以 `image-map.md` 的描述为准，不猜图、不编造图的内容
